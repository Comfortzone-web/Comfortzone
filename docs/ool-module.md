# OOL List

Inventory → OOL List is available to Admin and Staff. The opening migration loads the approved supplier workbook: 184 material lines, 887 units, AED 2,985,224.18 excluding VAT. “Removed” annotations are intentionally ignored. These are opening balances, not reconstructed original PO or receipt histories.

## Data and migration

`ool.js` owns the OOL ledger. At first server startup it captures existing PO IDs as excluded and loads `data/ool-opening.json`. Existing POs are not backfilled. Future official POs for Daikin Airconditioning LLC create Awaiting OC lines; future drafts become eligible when issued. Retrying PO saves does not duplicate OOL lines.

No SQL schema migration is needed: the app already stores JSON documents. OOL uses its own `ool:v1` document in the configured Supabase app-data table, or `data/ool.json` in local mode. Supabase writes use revision compare-and-swap, including insert-only initialization. Local writes are serialized within one server process and committed with atomic file replacement. Run only one application process for local JSON storage; multiple server processes require Supabase. Unlike the legacy shared store, OOL does not silently fall back to local storage after a Supabase error.

Collections: material lines, OC verification/revisions, request groups and lines, confirmations/follow-ups, receipt allocations, import snapshots, and audit events. Prices are integer fils. Original supplier amounts and original OC amounts remain separate from current balance values.

## Operations

- Add OC supports manual/oral confirmation and PDF/image/XLSX extraction with mandatory review. Quantities are cumulative per material line, and may be partially confirmed. Use **Split OC line** for an unconfirmed portion that will have a separate SD/SOR. Row-level SD/SOR fields support different references per material. Committed references cannot be silently reassigned. OC source files are retained in the existing upload infrastructure.
- Request Delivery reserves only available quantities after **Mark as Requested**. Copying alone does not reserve stock. Each request retains its own grouping, prices, references, email contents and delivery details. Delivery confirmation can be partial. Follow-up copying only records activity; it does not create another commitment.
- Hover-only request and material delete controls require confirmation. Whole requests can be removed only before any quantity is delivery-confirmed or received. Removing a partially confirmed material releases its pending balance and retains its confirmed quantity. Removed entries are hidden from the register; original quantities and audit records remain internally available.
- Supplier DN verification extracts and permits editing SD Document beside Detected Qty. A confirmed warehouse receipt remains the only stock-in transaction. On confirmation (or saving an already-confirmed receipt), unique SD + model matches against OOL delivery requests allocate automatically and update received quantities. Repeat confirmations do not duplicate allocations. Receipt quantities above the remaining OOL balance are capped to that balance. Ambiguous matches open the allocation review instead of guessing. Unallocated receipts can also be found under **More → Match received materials**.
- Direct project delivery verification retains SD per material and displays the same SOR/PO match hints. Saving verified direct delivery records automatically allocates unique SD + model matches, including edits to existing records. It clears OOL without adding warehouse stock; ambiguous matches use allocation review. Existing receipts without SD can be edited before allocation. Ambiguous SD/model matches require an explicit line selection; allocate a partial receipt to one line, then reopen the source to allocate its remaining quantity to another matching line if necessary.
- OOL receipts follow their saved source records. Saving a Supplier DN or direct delivery retains matching model + SD allocations, releases removed/unmatched quantities, and allocates newly eligible matches. Deleting/cancelling a Supplier DN, removing a direct upload, or deleting its project releases the corresponding OOL delivery quantities. Existing delivery confirmations remain in place. Warehouse stock and project BOQ quantities continue to follow their own source records. **Recent Activity** is read-only; allocation correction controls are not shown.
- Admin Excel reconciliation previews new lines, quantity and price differences. Supplier Open Qty is an absolute remaining balance, not an additive quantity. Existing delivery requests and project overrides survive reconciliation; reductions below committed quantities are rejected. Omitted rows are not automatically deleted.

The **Delivered List** tab shows allocated receipt quantities only, with SOR/SD, actual DN number/date, project/PO, model and quantity. Allocations split across delivery requests are merged for the same DN/material line; partial receipts appear for their received quantity. Admin-released allocations disappear from this view. PO/SOR filters, search, pagination and quantity totals are supported.

Supplier DN and Direct Delivery match Model + SD against delivery requests first. If none match, an Order Confirmed OOL line is eligible as an OC fallback; the UI labels it “Match with OC SOR (PO)”. Unconfirmed PO quantities are excluded, ambiguous matches require review, and only received quantities are deducted. Fully received lines become Delivered.

## UI and integrations

`public/ool-ui.js` and `public/ool.css` isolate OOL rendering and styling. `public/index.html` adds the submenu and assets. `public/app.js` adds the OOL view, PO Add OC action, SD fields and receipt-review entry points. `server.js` adds authenticated routing, future PO synchronization, extraction fields and source-lock checks. Local Inter is reused; table scrolling is contained at smaller sizes.

Tracked Daikin PO edits synchronize added models, pending quantities, PO references and project metadata into OOL. New models and extra quantities not yet covered by OC appear as Awaiting OC. Confirmed SD/SOR, OC prices, requests and receipts remain intact; edits below confirmed quantities or removing confirmed models are rejected before the PO is saved. Startup repairs missing lines for already-tracked POs without backfilling excluded or untracked older orders.

The selected-material toolbar includes a red delete icon for Awaiting OC and Order Confirmed materials. Deletion requires confirmation and is rejected for active delivery requests or received quantities. Deleted records are retained internally with user/time metadata, removed from live OOL balances, and excluded from unchanged tracked-PO synchronization. Purchase Orders themselves are not deleted or edited by this action.

Verify Order Confirmation offers **Undo split** on unconfirmed split rows. After confirmation, the split quantity merges back into its original row, preserving the parent's existing confirmed quantities, SD/SOR and delivery allocations. Nested split relationships are retained. Older splits are recognized by the same PO item/model; rows with their own confirmation or delivery history cannot be merged.

Excel reconciliation first matches the supplier row identity, then PO/model/SD/SOR, then a unique tracked PO/model with unconfirmed quantity. PO matching ignores formatting punctuation, spaces and case but retains revision suffixes and numbers. The preview labels links as **Match PO / confirm order**; applying fills SD/SOR, confirmed quantity and OC price on the tracked PO line and records the Excel OC. Partial confirmations under another SD/SOR use a separate linked OC portion while preserving the original confirmed portion. Ambiguous matches, unknown models on a tracked PO, and quantities above PO capacity block application. Reuploading an already-applied file compares the current ledger and can restore missing rows, update differences or repair pending PO links; older unlinked import rows are merged with their request/receipt references preserved.

The OC dialog defaults quantity to PO quantity minus already confirmed quantity; SD, SOR and unit price start empty for the new confirmation. Saving this dialog uses additional-quantity semantics. A subsequent confirmation creates a linked OC portion so the previous quantity, SD/SOR, price, requests and receipts stay unchanged. Enter a price for each positive quantity; rows set to zero are skipped. Legacy cumulative API revisions remain supported separately.

For imported OOL materials without a tracked ERP PO, reconciliation sets Order Qty and confirmed quantity to supplier Open Qty plus already received quantity. The original imported order quantity is retained internally. Older rows whose confirmed quantity already exceeds the displayed order quantity are repaired at startup without altering balances, requests or receipts. Tracked ERP PO quantities remain capped by their actual PO lines.

Import hashes are historical references, not a permanent block against reusing a workbook. Reapplying a workbook that already matches current OOL returns success without adding rows or another import snapshot. If rows were deleted or balances changed, the same workbook can be reviewed and applied again, with the same quantity, PO matching and allocation checks.

Repeated model rows with the same PO/SD/SOR are distinguished by the supplier item number. For example, item 330 with quantity 2 and item 340 with quantity 5 remain separate records totaling 7. Reference-only matching is used only for a unique supplier row. Genuine conflicts appear in pastel red with a count, affected model/PO and **Show first conflict** control; ordinary new/changed rows remain pastel orange and do not block Apply.

Import preview returns warnings for material rows omitted due to missing/invalid model, SD, SOR, PO, quantity, price or supplier amount. A bottom-of-preview alert lists physical Excel row numbers, model names, missing fields and known excluded value. Valid zero quantities/prices remain valid. The footer and existing Apply confirmation remind the user that incomplete rows are excluded; otherwise-valid rows remain applicable. No missing references are guessed.

OOL navigation mounts immediately without waiting for the general Inventory request. Existing in-memory OOL content remains visible while refreshing; first load uses a structured skeleton. Successful ledger mutations reuse the server-confirmed response, avoiding a second full GET. Manual Refresh and navigation still fetch current data. Compact browser responses omit deleted/merged records and historical row snapshots, while retaining the latest activity. Balance totals use a single pass through requests/receipts. Excel upload has a header progress indicator, disables duplicate uploads/apply while checking, and Apply/confirmation/request buttons show progress until server acknowledgement. Failed saves retain the dialog and error message; no unconfirmed success is displayed.

Admin: Application Settings → Staff Purchase Order Access. Select a staff login, select a supplier, choose View or Edit and add it; save the selected staff account. Only assigned suppliers appear in the compact permission list. Select one Staff login and assign supplier View/Edit permissions; Edit always includes View. Staff defaults to no PO access. Allowed suppliers cover all historical and current POs. Staff never sees the Supplier directory, cannot manage suppliers or delete POs, and can create/update only suppliers granted Edit. PDF generation uses the permitted saved PO, and source attachments are authorized independently. Revocation is enforced on the next request. Only Daikin qualifies for OOL; PO visibility grants do not change OOL eligibility. Staff should refresh after Admin changes access to update sidebar controls.
